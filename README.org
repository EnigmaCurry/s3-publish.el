#+title: Publish to S3 from Emacs

#+html: <p align="center"><img src="images/s3-publish-logo.png" alt="s3-publish.el logo" width="300"></p>

This is an Emacs package that quickly publishes any buffer, region, or
file to S3 and the web (AWS S3, DigitalOcean spaces, etc.).

Example: https://org.nyc3.digitaloceanspaces.com/8ik4g-8vbao-w4adc-nsjxe-qr0uo.html ([[https://org.nyc3.digitaloceanspaces.com/index.html][index]])

------------------------------------------------------------

=M-x s3-publish-buffer=

The intended purpose is for easily publishing files on the web, using S3
as a paste-bin service. The object keys of the uploaded files will be
renamed with a salted hash of the path + file extension, so the URLs
are serviceable, but not really that pretty:

: https://my-bucket.region.provider/c6ej4-zk2ah-vvjq8-7w244-9bjxp.txt

This long URL is fine if you're just copy and pasting the link into a
chat message. Since the hash is salted, it is not practical to guess
the URL, therefore the contents are only accessible to those whom you
share it with.

There is also an option to create an HTML index and RSS feed if you
wish to make these URLs discoverable.

Org and Markdown buffers get special treatment: they are exported to
styled, self-contained HTML pages (via Org's HTML exporter, so both
look the same), published alongside their original source, and listed
as a single entry in the feed. The styling is configurable -- see
[[#html-theme][Theming the published HTML]] and [[#html-anchors][Headings, anchors and
the table of contents]].

** Dependencies

This package requires the following external tools:

 * =s3cmd= - Required for all S3 operations.
 * =s3fs= - Optional, required only for mounting S3 buckets as local filesystems.
 * =fusermount= - Optional, required for unmounting s3fs mounts.

These dependencies can be installed via your OS package manager.

** Installation

This package is not on MELPA (yet). The package is self-contained in
one file: [[https://github.com/EnigmaCurry/s3-publish.el/blob/master/s3-publish.el][s3-publish.el]].

You can declare the dependency in your config with use-package +
[[https://github.com/radian-software/straight.el][straight.el]], and it will pull it directly from this git repository:

#+begin_src emacs-lisp
  (use-package s3-publish
    :straight
    (s3-publish
     :type git
     :repo "https://github.com/EnigmaCurry/s3-publish.el.git")
     ;;; If you're using general.el, set a keybinding this way:
     ;; :general
     ;; ("C-c p" 's3-publish)
    )

  ;;; If you're not using general.el, set a keybinding this way:
  ;;(global-set-key (kbd "C-c p") 's3-publish)
#+end_src

(See [[https://github.com/noctuid/general.el][general.el]] for declarative keybindings in use-package)

** Configuration

You must configure a profile for each S3 bucket you want to publish
to. Run =M-x s3-publish-manage-profiles= to interactively manage your
profiles. Your profiles will be stored in your Emacs' custom.el file
as =s3-publish-profiles=.

*** Example: DigitalOcean spaces

Create a bucket:

 * Login to your DigitalOcean account at cloud.digitalocean.com
 * Go to the =Spaces Object Storage= page.
 * Click =Create Bucket=.
 * Select the desired data center region, e.g. =nyc3=.
 * Choose a unique name for the bucket, e.g. =gargleblaster=.
 * Don't enable CDN for this basic example.
 * Finalize the creation of the bucket.

Create the access key:

 * Go to the bucket =Settings= page.
 * Click =Create Access Key=
 * Choose =Read/Write/Delete= permission.
 * List all of the buckets the access key is allowed to use (one by
   default).
 * Enter a descriptive name for the key like =mymachine-s3-publish-emacs=
 * Finalize the creation of the Access Key.
 * Copy the Access Key ID and the Secret Access Key. The secret will
   not be shown again.

Setup s3-publish in Emacs:

 * Run =M-x s3-publish-manage-profiles=.

This will open up a buffer named =s3-publish-profiles=, which will
initially display =No s3-publish profiles defined=.

In the minibuffer you should see a list of actions you can perform:

 * Add
 * Remove
 * Edit
 * Done

Add a new profile:

 * Choose the =Add= action.
 * Enter the =Profile name=:, this can be any name you choose, perhaps
   the same name as the bucket, e.g. =gargleblaster=.
 * Enter the =Endpoint URL=, which is listed at the top of the bucket
   page, e.g. =https://gargleblaster.nyc3.digitaloceanspaces.com=
 * Enter the bucket name (again). e.g. =gargleblaster=.
 * Choose whether you want the files to be made public or not. =Make
   files public? (y or n)=

You should now see the =s3-publish-profiles= buffer has been updated
to show your configured profiles. Select =Done= when finished.

** Prepare credentials auth-source

The S3 access keys and secret keys are not stored in the profile, but
are accessed through [[https://www.gnu.org/software/emacs/manual/html_mono/auth.html][Emacs' configurable auth-source system]].

To create a simple unencrypted auth-source, create a file in your home
directory. Create the file =~/.authinfo= and enter the credentials for
the profile:

#+begin_src text
machine s3-publish-gargleblaster login XXXXXXXXXXXXXXXXXX secret XXXXXXXXXXXXXXXXXXXX
#+end_src

The profile is matched against the authinfo machine name. Here's the
breakdown on the authinfo syntax:

 * The first word is literally =machine=.
 * The second word must start with =s3-publish-= and then the name of
   the profile, e.g. =gargleblaster=.
 * The third word is literally =login=.
 * The fifth word is the S3 Access Key credential.
 * The sixth word is literally =secret=
 * The seventh word is the S3 Secret Key credential.

Make sure to save the file, and then inform Emacs to reload this file:
=M-x auth-source-forget-all-cached=.

Emacs auth-source supports many different backends that are more
secure than this plain authinfo file, including:

 * Gnome Keyring
 * KDE Wallet
 * KeepassXC
 * Unix password store

To set these up is left as an exercise to the reader.

** Usage

Every command that asks for an S3 profile starts on the profile you
used last, so =RET= publishes to the same place again. It is never
chosen without asking. With =savehist-mode= enabled, the last profile
is remembered across Emacs sessions too.

*** Publish buffer

You can publish your current buffer:

 * =M-x s3-publish-buffer=
 * From the list, select the S3 profile destination.
 * The buffer will be immediately uploaded to S3.
 * The URL will be printed in the minibuffer and copied to
   =kill-ring=.

If you chose to allow public access, the URL will start with
=https://=, otherwise it will start with =s3://=.

The URL should have a file extension that is derived from the buffer
name.

The buffer can even contain non-text data, e.g. images. In this case,
choose the encoding type =raw=.

*** Publish Region

Like publishing buffers, you can publish a select region of text.

 * Select a region of text in any buffer.
 * =M-x s3-publish-region=.
 * From the list, select the S3 profile destination.
 * The region will be published with a =.txt= extension.
 * The URL will be printed in the minibuffer and copied to
   =kill-ring=.

*** Publish Org Buffer

In org-mode you can export the buffer to HTML and publish it in one
step:

 * =M-x s3-publish-org-buffer=
 * From the list, select the S3 profile destination.
 * The buffer will be exported to HTML and immediately uploaded to S3.
 * The original =.org= source is uploaded alongside it, under the same
   key but with the =.org= extension, and linked at the bottom of the
   HTML page.
 * The URL will be printed in the minibuffer and copied to
   =kill-ring=.

**** Tangling before publishing

Literate documents often evaluate code during export that runs the
files they [[https://orgmode.org/manual/Extracting-Source-Code.html][tangle]]. Exporting without tangling first runs stale or
missing files. To be asked whether to tangle before each publish, set:

#+begin_src emacs-lisp
  (setq s3-publish-org-tangle 'ask)
#+end_src

Tangling overwrites the tangled files, so it is never done without
asking, and documents with nothing to tangle are not asked about. The
default, =nil=, never tangles.

A document can declare what it needs:

 * =#+S3_PUBLISH_TANGLE: t= marks a document that must be tangled. It
   is still asked about, and publishing it is an error while
   =s3-publish-org-tangle= is =nil=, rather than uploading a page made
   from stale files.
 * =#+S3_PUBLISH_TANGLE: nil= is never tangled or asked about.

Only =s3-publish-org-buffer= tangles. Regions and Markdown are
exported from a temporary copy, where relative tangle paths would
point at the wrong place.

*** Publish Markdown Buffer

Markdown buffers work exactly the same way, and produce exactly the
same look:

 * =M-x s3-publish-markdown-buffer=
 * From the list, select the S3 profile destination.
 * The buffer will be exported to HTML and immediately uploaded to S3.
 * The original =.md= source is uploaded alongside it, under the same
   key but with the =.md= extension, and linked at the bottom of the
   HTML page.
 * The URL will be printed in the minibuffer and copied to
   =kill-ring=.

Markdown is not rendered by a separate Markdown-to-HTML converter.  It
is first translated to Org markup, then handed to Org's own HTML
exporter. Published Markdown is therefore styled identically to
published Org -- same stylesheet, table of contents, section
numbering, source block containers and postamble. See [[#html-theme][Theming the published
HTML]].

The built-in translator needs no external programs and understands:

 * ATX (=#=) and setext (====-=) headings
 * YAML front matter (=title:= and =description:= become =#+TITLE:= and
   =#+DESCRIPTION:=)
 * =**bold**=, =*italic*=, =***both***=, =~~strikethrough~~= and
   =`inline code`=
 * Fenced code blocks, with or without a language, using backticks or
   tildes
 * Ordered, unordered, nested and task (=- [x]=) lists
 * Links, images, autolinks and footnotes
 * Tables, blockquotes and thematic breaks
 * Backslash escapes

Unless the front matter supplies a title, a level-1 heading is promoted
to =#+TITLE:= when it opens the document, or when it is the only one in
it. This is how Markdown is conventionally written -- and how nearly all
generated Markdown looks -- so the published page gets a proper document
title instead of a numbered first section.

If the promotion leaves no level-1 heading behind, the remaining
headings shift up a level to take its place. If one remains, levels are
left alone, so nothing is dropped or flattened onto its own children.

A later level-1 heading repeating the title exactly is dropped, keeping
its body. Generated Markdown often restates its own title partway down;
left in, it renders the title a second time and lists it twice in the
table of contents.

Indented (four space) code blocks and raw inline HTML are passed
through as ordinary text rather than converted. If you want full
CommonMark fidelity instead, point =s3-publish-markdown-to-org-command=
at an external converter that writes Org markup, for example:

#+begin_src emacs-lisp
  (setq s3-publish-markdown-to-org-command "pandoc -f gfm -t org")
#+end_src

The result is still rendered by Org's HTML exporter, so the look is
unchanged.

*** Images
:PROPERTIES:
:CUSTOM_ID: local-images
:END:

An image that lives on your disk -- =[[file:diagram.png]]= in Org,
=![shot](shot.png)= in Markdown -- would be a broken link on the
published page, since nobody else can read your files. So when an Org
or Markdown document is published, its local images are carried along:

 * By default each one is embedded in the page itself, as a =data:=
   URI, so the page stays a single self-contained file.
 * An image bigger than =s3-publish-html-inline-image-max-size= (1 MiB)
   is uploaded beside the page instead, and the page links to it. Its
   key comes from the image's own path, so republishing replaces it
   rather than adding another copy.

Relative paths are resolved against the document's own directory.
Images already on the web are left alone, as is a link to an image that
cannot be read (with a warning).

#+begin_src emacs-lisp
  ;; Always upload images rather than embedding them:
  (setq s3-publish-html-local-images 'upload)
  ;; Or leave image links exactly as Org wrote them:
  (setq s3-publish-html-local-images nil)
#+end_src

*** Republish on save

=M-x s3-publish-on-save-mode= turns a buffer into a live document: it
asks once which profile to publish to, and from then on every save
republishes the buffer without asking. Org and Markdown buffers publish
as documents; any other file is uploaded as itself. A file's URL comes
from its path, so it never changes -- a page you have shared keeps
showing your latest save. With background uploads (the default),
saving does not wait for the upload.

Turning the mode on publishes nothing until the next save. Publishing
on save never tangles an Org buffer. A file can turn the mode on for
itself, with its profile, in its local variables:

#+begin_src org
  # Local Variables:
  # s3-publish-on-save-profile: "default"
  # mode: s3-publish-on-save
  # End:
#+end_src

*** Theming the published HTML
:PROPERTIES:
:CUSTOM_ID: html-theme
:END:

Org's own export stylesheet is deliberately minimal, which makes
published pages look unstyled. =s3-publish-html-theme= decides the CSS
that gets inlined into every page it publishes:

#+begin_src emacs-lisp
  ;; The built-in theme (the default). A dark theme adapted from the
  ;; author's simple_dark Emacs HTML theme, and self-contained.
  (setq s3-publish-html-theme 'default)

  ;; Your own stylesheet, read from disk at publish time.
  (setq s3-publish-html-theme "~/.emacs.d/theme/simple_dark.css")

  ;; Or CSS inline.
  (setq s3-publish-html-theme "body { max-width: 50em; margin: auto; }")

  ;; Or nothing at all: leave your Org HTML export settings untouched.
  (setq s3-publish-html-theme nil)
#+end_src

The built-in theme is =simple_dark= plus rules for the markup that theme
does not cover: source block syntax classes, self-linking headings, the
table of contents sidebar, example blocks, images, and the source-file
link s3-publish appends to the bottom of every page. If you point
=s3-publish-html-theme= at =simple_dark.css= on disk instead, you get the
original without those additions.

The built-in theme follows each reader's own preference: it is light or
dark to match their browser or system setting (=prefers-color-scheme=),
and dark when a browser does not say. To fix it to one scheme for
everyone instead:

#+begin_src emacs-lisp
  (setq s3-publish-html-color-scheme 'dark)  ; always dark
  (setq s3-publish-html-color-scheme 'light) ; always light
#+end_src

The theme belongs to the publisher rather than to the document, which
is what lets Markdown be themed at all -- Markdown is exported from a
temporary directory, so a document-relative =#+SETUPFILE:= pointing at a
stylesheet cannot resolve there.

A document that sets its own =#+HTML_HEAD:= still overrides the theme, so
per-document styling keeps working.

The CSS is always inlined, never linked, so a published page stays
self-contained: there is no stylesheet to upload beside it and nothing
to break when the page is viewed from a different origin. For the same
reason, source blocks are exported with CSS classes rather than with
the colours of your running Emacs theme baked in, so code is coloured
by the page theme instead of fighting it.

Each source block is labelled with its language by the theme. Advice
your config places on =org-html-src-block=, such as a custom header
for local exports, is ignored while publishing so it does not clash
with that label; the advice itself is left in place. To publish with
it applied, or to ignore advice on other exporter functions, set
=s3-publish-html-ignore-advice=:

#+begin_src emacs-lisp
  ;; Default: source blocks are exported unadvised.
  (setq s3-publish-html-ignore-advice '(org-html-src-block))
  ;; Keep all of your advice.
  (setq s3-publish-html-ignore-advice nil)
#+end_src

Every source and example block also gets a /Copy/ button that copies
its contents, without line numbers, to the clipboard. It is a small
inline script, so like the theme it needs nothing uploaded beside the
page. It is independent of the theme and survives a document's own
=#+HTML_HEAD:=; a single document can opt out with =#+OPTIONS:
html-scripts:nil=, or you can turn it off everywhere:

#+begin_src emacs-lisp
  (setq s3-publish-html-copy-button nil)
#+end_src

Published pages also carry an icon, inlined as a =data:= URI for the same
self-contained reason:

#+begin_src emacs-lisp
  ;; The built-in icon (the default).
  (setq s3-publish-html-favicon 'default)

  ;; Your own image, inlined. Media type comes from the extension.
  (setq s3-publish-html-favicon "~/.emacs.d/theme/icon/emacs.ico")

  ;; Or an href used verbatim, to link rather than inline.
  (setq s3-publish-html-favicon "https://example.com/icon.png")

  ;; Or no icon at all.
  (setq s3-publish-html-favicon nil)
#+end_src

Since the icon rides along in every page, keep it small: the built-in
one is a 32x32 PNG of about 3kB encoded. A multi-size =.ico= is usually
far larger -- the 34kB five-size =emacs.ico= would roughly quadruple a
typical published page.

*** Headings, anchors and the table of contents
:PROPERTIES:
:CUSTOM_ID: html-anchors
:END:

Org gives a heading an =id=, reachable only from the table of contents.
Published pages make every heading a link to its own anchor, so
clicking any heading puts that anchor in the address bar, ready to copy
and share. Headings still read as headings; the link reveals itself on
hover. Turn it off with:

#+begin_src emacs-lisp
  (setq s3-publish-html-self-link-headlines nil)
#+end_src

For Markdown, each heading also gets a =:CUSTOM_ID:= derived from its
text, so anchors are readable and, more importantly, stable:

: https://my-bucket.region.provider/c6ej4-....html#getting-started

Org's generated ids are content hashes that change on every export, so
a link shared against one would stop resolving the next time you
published the document. Duplicate headings are uniquified (=#notes=,
=#notes-2=). Org buffers get the same treatment wherever they set their
own =:CUSTOM_ID:=.

The table of contents is headed by the document's own title -- its first
header -- rather than by the words "Table of Contents", with the entries
nested beneath it. The title links back to the top of the page. A
document without a title gets no heading there at all.

On a screen wide enough for it (1100px), the table of contents moves
out of the document flow into its own column on the right, narrower
than the content and sticky, so it stays visible however far down you
scroll. If the list is longer than the window it scrolls on its own,
while its title stays put. Below that width it falls back to sitting
inline above the content, and a document published without a table of
contents keeps the full width.

Org emits its postamble as a sibling of the content div, which would put
it -- and the source-file link -- below the sidebar rather than below the
text. Both are moved inside the content area when publishing, so they
stay in the content column at any width.

*** Publish from dired mode

You can publish multiple files at once from a dired buffer:

 * Open any directory in =dired-mode=.
 * Mark multiple files with the =m= key (directories not supported).
 * =M-x s3-publish-dired-upload-files=.
 * All of the marked files will be uploaded to S3.
 * All of the URLs will be printed in the minibuffer and copied to
   =kill-ring=.
 * List of URLs output are separated by newlines.

*** Publish what I mean

The =s3-publish= command automatically detects your current editing
context and dispatches the appropriate S3 publishing action (Do What I
Mean). Its behavior is determined by the following priorities:

- *Region selected:*

  If you have an active region, the command calls =s3-publish-region=
  to upload the selected text to S3.

- *In org-mode buffer:*
  - Without a prefix argument, it exports your Org buffer to HTML and
    uploads it using =s3-publish-org-buffer=.
  - With a universal (prefix) argument (e.g., =C-u M-x s3-publish=),
    it removes both the =.org= source and its published HTML from S3
    by calling =s3-publish-remove-document=.

- *In a Markdown buffer:*
  - Without a prefix argument, it exports your Markdown buffer to HTML
    and uploads it using =s3-publish-markdown-buffer=.
  - With a universal (prefix) argument, it removes both the =.md=
    source and its published HTML from S3 by calling
    =s3-publish-remove-document=.

  Markdown buffers are detected by =markdown-mode= (and derivatives
  such as =gfm-mode=), falling back to the file extension (=.md=,
  =.markdown=, =.mdown=, =.mkd=, =.mkdn=) so a Markdown file is
  recognised even without =markdown-mode= installed.

- *In dired buffer:*
  - Without a prefix argument, it uploads the marked files using
    =s3-publish-dired-upload-files=.
  - With a prefix argument, it removes the marked files from S3 using
    =s3-publish-dired-remove-files=.

- *Other buffers:*
  - Without a prefix argument, the entire buffer is published using
    =s3-publish-buffer=.
  - With a prefix argument, it removes the file backing the current
    buffer from S3 by invoking =s3-publish-remove-file=.

To make this functionality even more accessible, you can bind it to a
convenient key sequence. For example, to bind it to =C-c p=, add the
following to your Emacs configuration:

#+BEGIN_SRC emacs-lisp
  (global-set-key (kbd "C-c p") 's3-publish)
#+END_SRC

This key binding lets you quickly invoke the context-sensitive
publishing command from anywhere within Emacs.

** Updating files

The S3 keys and public URLs use a filename that is a hash of the local
path of the file. This means that if you upload the same file twice,
it will keep the same key/URL. However, there are two exceptions:

 * =s3-publish-buffer=
 * =s3-publish-region=

Both of these create temporary files with random names in order to
export them. Therefore these will always make new S3 keys.

** Choosing a document's URL

A document is normally published under a key hashed from its path. To
choose the name yourself, set it in the document -- in Org with a
keyword, in Markdown in its front matter:

#+begin_src org
  ,#+S3_PUBLISH_KEY: notes/my-post
#+end_src

#+begin_src markdown
  ---
  s3_publish_key: notes/my-post
  ---
#+end_src

The page is then published as =notes/my-post.html= and its source as
=notes/my-post.org= (or =.md=); writing =my-post.html= means the same.
Removing, signing, live editing and republishing all follow the name.
A name is letters, digits, =.=, =_= and =-=, with =/= between parts.

A name is yours to choose, so it is not checked against what is
already in the bucket: two documents with one name replace each other.
Naming a document that was already published moves it; the objects
under its old, hashed key stay until you remove them (do that first,
with =C-u M-x s3-publish=).

** Background uploads

Uploading, and updating the RSS feed and HTML index, happen in the
background, in a separate =emacs --batch= process, so Emacs stays
usable while they run. A URL depends only on the file and the profile,
so it is known before the upload starts: it is copied to the
=kill-ring= straight away, and a message reports when the upload has
finished. If an upload fails you get a warning; the output of every
upload is kept in the =*s3-publish-log*= buffer.

Uploads run one at a time, in order, since each one edits the shared
feed and index. A document still waiting for its turn is replaced by a
newer upload of the same document. Emacs asks before exiting while
uploads are unfinished.

Exporting, prompts and credential lookup still happen in Emacs before
the upload starts; only the network traffic moves. Removing files
always happens in the foreground. To upload in the foreground too, as
before:

#+begin_src emacs-lisp
  (setq s3-publish-async nil)
#+end_src

** Private buckets and expiring links

With a profile that does not make files public, publishing copies a
signed https URL: anyone can open it, but only for a week. The links
inside a published page, to its source and to images uploaded beside
it, are signed for as long, so they expire together; republishing (or
saving in a live edit) signs them all afresh. Change how long links
work, or go back to =s3://= URIs, which only someone holding your
credentials can use:

#+begin_src emacs-lisp
  (setq s3-publish-signed-url-expiry "3d")  ; a number, then s, m, h, d or w
  (setq s3-publish-signed-url-expiry nil)   ; s3:// URIs
#+end_src

A document can set its own, which republishing, on-save mode and live
edits all keep to -- in Org with a keyword, in Markdown in its front
matter:

#+begin_src org
  ,#+S3_PUBLISH_LINK_EXPIRY: 2d
#+end_src

#+begin_src markdown
  ---
  s3_publish_link_expiry: 2d
  ---
#+end_src

=nil= there means an =s3://= URI for that document. Seven days is the
longest a signed URL works on DigitalOcean (and AWS), so a longer
expiry is an error rather than a link that dies early; for a provider
that allows more, raise =s3-publish-signed-url-max-expiry=.

A page opened through a signed link says so at the bottom, in green,
with a countdown to when the link stops working; if the page is left
open past then, the notice turns red. Opened any other way it shows
nothing. Turn it off with =(setq s3-publish-html-link-expiry-notice nil)=.

To sign a link on demand -- for a file published earlier, or to hand
out a link from a public bucket that stops working -- use:

 * =M-x s3-publish-sign-url=
 * Select the profile.
 * Enter a URL, an =s3://= URI or a key. It defaults to what the
   current buffer is published as.
 * Enter how long the link should work.

Links are signed locally by =s3cmd signurl=, which uses AWS signature
version 2. DigitalOcean Spaces, MinIO and most S3 work-alikes accept
it; AWS regions opened since 2014 do not.

** Caching

Every upload is sent with a =Cache-Control: no-cache= header, so
browsers and CDNs check with the bucket before reusing a cached copy.
A republished page, the HTML index and the RSS feed therefore show
their new contents straight away. Set =s3-publish-cache-control= to
another value (e.g. ="max-age=300"=) to cache longer, or to =nil= to
send no header at all.

** Listing published files

=M-x s3-publish-list= shows everything published with a profile, newest
first. A profile that keeps an RSS feed is listed from the feed, with
the titles things were published under. Any other profile -- or any
profile, with a prefix argument (=C-u M-x s3-publish-list=) -- is
listed from the bucket itself (=s3cmd ls=): every object in it, with
its size, including the feed, the index and uploaded images. On a line:

| Key   | Action                                                    |
|-------+-----------------------------------------------------------|
| =RET= | Open the file in a web browser                            |
| =w=   | Copy its URL                                              |
| =s=   | Copy a signed URL that expires                            |
| =D=   | Delete it from the bucket, the feed and the index         |
| =t=   | Switch between the feed and the whole bucket              |
| =e=   | Edit it live: every save republishes it                   |
| =g=   | Fetch the list again                                      |

Deleting a document deletes its source file along with its HTML page.

*** Editing a published file live

Press =e= on a line, or run =M-x s3-publish-edit= with a URL, to edit a
published file without its original on disk. For a document's HTML page
its Org or Markdown source opens; anything else opens as itself. The
file is downloaded to a temporary directory with
=s3-publish-on-save-mode= turned on, and every save republishes it to
the same key -- the same URL, the same entry in the feed and index. It
works like a live editor for what you have published. Killing the
buffer deletes the temporary copy; your original file, if you still
have it, is not touched.

Local images are not downloaded. Instead, published pages record each
image's original link, so saving keeps the images the page was
published with. A page published before s3-publish recorded them loses
its images when edited this way, until it is published once more from
the original file.
A file in a private bucket opens through a signed URL that works for an
hour.

** Removing URLs

You can remove the objects by supplying the URLs:

 * =M-x s3-publish-remove-urls=

You may enter URLs to delete, one per line.

You may also remove files from dired mode:

 * Mark files in dired mode buffer.
 * =M-x s3-publish-dired-remove-files=

This will delete the remote objects for the given files (if they
exist). It will not remove them locally. If the HTML index and RSS
feed is enabled, the URL will be removed from the feed as well.

Documents published with =s3-publish-org-buffer= or
=s3-publish-markdown-buffer= upload /two/ objects: the rendered HTML and
the original source, sharing one key and differing only in extension.
To remove both at once, along with their shared entry in the RSS feed
and HTML index, use:

 * =M-x s3-publish-remove-document=

This is what =C-u M-x s3-publish= calls in an Org or Markdown buffer.
Removing such a document with =s3-publish-remove-file= instead deletes
only the source and leaves the HTML, and its feed entry, behind.

** Lifecycle

You can set the S3 lifecycle of the bucket to let objects expire
automatically. You will usually need an increased API permission level
to perform this action (e.g. on DigitalOcean spaces you must select
the =All permissions= option, which gives full access to ALL your
buckets.)

 * =M-x s3-publish-bucket-lifecycle=
 * Select the profile to manage.
 * Enter the number of days that objects may live before expiration.
   e.g., =1=, =10=, or leave blank to delete the lifecycle config.

If you don't have adequate permission, you will see the error in the
mini buffer.

** Mount S3 buckets as filesystems

You can mount your S3 bucket as a local filesystem using s3fs:

 * =M-x s3-publish-s3fs-mount=
 * Select the S3 profile to mount
 * Enter the local directory where you want to mount the bucket
 * The bucket will be mounted at the specified location
 * A dired buffer will open showing the contents of the mounted bucket

To unmount the bucket:

 * =M-x s3-publish-s3fs-unmount=
 * Select the mounted directory
 * The mount will be removed and any associated dired buffers closed

This feature requires the =s3fs= command-line tool to be installed on your system.

** Alternative credentials for admin operations

Some operations like setting bucket lifecycle policies or configuring
website hosting require elevated permissions. For these operations,
s3-publish can prompt you to select alternative credentials.

You can add additional credentials in your auth source with different
machine names, and s3-publish will present them as options when
performing operations that may require higher privileges.

For example, you might have regular credentials for normal uploads:
#+begin_src text
machine s3-publish-gargleblaster login REGULAR_ACCESS_KEY secret REGULAR_SECRET_KEY
#+end_src

And separate admin credentials with full permissions:
#+begin_src text
machine s3-publish-admin login ADMIN_ACCESS_KEY secret ADMIN_SECRET_KEY
#+end_src

When performing administrative operations, s3-publish will give you
the option to select an alternative credential from your auth source.

** Publishing from scripts and agents

The =s3-publish-api-*= functions drive s3-publish from outside Emacs,
e.g. through =emacsclient --eval=. They never prompt, take the profile
by name, leave the kill ring alone, and publish a file as it is on
disk without touching any buffer you have open:

| Function                 | Does                                              |
|--------------------------+---------------------------------------------------|
| =s3-publish-api-profiles= | List the profiles (no credentials)               |
| =s3-publish-api-publish=  | Publish a file; returns its URL, keys and job    |
| =s3-publish-api-status=   | Report on background uploads                     |
| =s3-publish-api-list=     | List the feed, or every object in the bucket     |
| =s3-publish-api-delete=   | Delete by URL or path, both halves of a document |
| =s3-publish-api-sign=     | Make a signed URL that expires                   |

*** Claude Code skill

=claude-skill/s3-publish/= is a [[https://docs.claude.com/en/docs/claude-code/skills][Claude Code skill]] built on this API, so
Claude can publish, list and delete files. Each command runs in its own
fresh =emacs --batch=, with none of your configuration: it reads only
your s3-publish settings (=s3-publish-profiles= and any other
=s3-publish-= options) from your custom file, and your credentials from
auth-source. Your running Emacs is never involved. No code in an Org
document is run unless you tell Claude to. Claude asks you which
profile to use when that is not clear, and before deleting anything.

Install it by linking it into your skills directory:

#+begin_src shell
  ln -s "$PWD/claude-skill/s3-publish" ~/.claude/skills/s3-publish
#+end_src

=claude-skill/s3-publish/s3p check= shows where your settings were read
from. Point =S3P_SETTINGS_FILE= at the file holding your
=(custom-set-variables '(s3-publish-profiles ...))= if it is not found.
